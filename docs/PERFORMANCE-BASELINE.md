# 번들·미디어·WebView 성능 기준값

측정일: 2026-08-31  
환경: Next.js 16.2.6, 프로덕션 Turbopack 빌드, Windows

## 재현 방법

```bash
next build && corepack pnpm perf:bundles
```

`tools/perf/measure-bundles.mjs` 가 아래 절차를 그대로 수행한다.

1. `node_modules/.bin/next.cmd build`로 프로덕션 빌드를 만든다.
2. 각 `.next/server/app/<route>/page_client-reference-manifest.js`가 참조하는
   `static/chunks/*.js`의 중복을 제거한 뒤 원본 크기와 gzip 크기를 합산한다.
3. 정적 자산은 `public` 아래 파일 크기를 직접 합산한다.

⚠ **손으로 재지 않는다.** 사람마다 중복 청크를 빼는지·gzip 설정이 어떤지가 달라져서,
그렇게 잰 숫자로는 "전후 비교" 라는 말 자체가 성립하지 않는다. 스크립트가 기준값
(아래 표)을 안에 들고 있어 실행하면 곧바로 증감이 나온다.

라우트 수치는 브라우저가 해당 라우트에서 참조할 수 있는 청크의 합이다. 공유 청크와
동적 청크가 있으므로 네트워크에서 항상 전부 다시 전송된다는 뜻은 아니며, 전후 비교용
기준값으로 사용한다.

### 읽는 법 — 늘어난 화면도 그대로 적는다

카탈로그를 물던 화면(`/plan`·`/routine`·`/exercises`)은 절반 아래로 내려갔다. 반대로
**세 화면은 늘었다**. 줄어든 것만 적으면 다음 사람이 "번들 다이어트는 끝났다" 고 믿게
되므로 같이 남긴다.

| 화면 | 증가 | 짐작되는 원인 |
|---|---:|---|
| `/running` | +16.2 KiB | 러닝 세션 기록·야외 러닝 작업(진행 중) |
| `/home` | +6.0 KiB | 주간 리포트 카드(2.3) |
| `/community` | +5.6 KiB | 커뮤니티·신고 작업(진행 중) |

세 화면 모두 **원래 가벼운 축**이라(150~400 KiB) 당장 손댈 일은 아니다. 다만 기능이
늘 때마다 조금씩 붙는다는 뜻이므로, 다음 기능을 넣을 때 이 표를 다시 돌려 본다.

Three.js/GLTF 코드가 포함된 동적 청크는 942.9 KiB 원본, 249.8 KiB gzip이다.
`/running`과 근육 선택 화면은 `next/dynamic`으로 이 청크를 초기 라우트 청크에서
분리하고 있다.

## WebView 메모리 측정 절차

실기기 연결 후 같은 APK와 동일 계정으로 아래 시나리오를 각각 3회 실행한다.

1. 앱 최초 실행 후 `/home`에서 30초 대기
2. `/plan` → `/plan/muscle` → `/routine` → 운동 상세 → `/running` 순회
3. 각 화면 진입 30초 후 `adb shell dumpsys meminfo app.helssu.twa`의 TOTAL PSS와
   Graphics 값을 기록
4. 홈으로 돌아온 뒤 60초 대기하고 회수된 메모리를 다시 기록
5. WebView 렌더러 종료와 `adb logcat`의 low-memory 경고 여부 확인

### 실측 (2026-09-02) — Galaxy S23 (SM-S911N), Android 16, 앱 v1.0.3(4)

⚠ 앱은 **원격 URL**을 로드하므로 이 수치는 **그때 배포돼 있던 웹**(2026-09-01 이전)
기준이다. 오늘 작업분(번들 −49%·MP4 −89%)은 **배포 후 다시 재야 한다** —
이 값은 그 비교의 '전' 이 된다.

| 홈 | 294,768 KB | 139,668 KB |
| 운동 | 273,368 KB | 119,308 KB |

**읽는 법** — PSS 는 화면을 옮겨도 260~316 MB 사이에서 오르내릴 뿐 **누적되지 않는다**.
운동모드가 가장 무겁고(316 MB, Graphics 155 MB), 홈으로 돌아오면 회수된다.
즉 이 빌드에서는 **화면 이동으로 새는 메모리가 관측되지 않았다**.

### 탭 순회 (2026-09-02)

하단 탭 6개(홈·운동·식단·캘린더·그룹·커뮤니티)를 **3바퀴 = 18회** 이동 + 운동모드
진입/중단까지 약 10분.

- **프로세스 PID 28133 이 처음부터 끝까지 유지** — 앱도 WebView 렌더러도 안 죽었다
- logcat **68,092줄**에 `app.helssu.twa` 관련 크래시·ANR·렌더러 종료·OOM **0건**
  (`onTrimMemory` 매치 27건은 전부 **다른 앱**의 것이었다 — 우리 것이 아니다)
- PSS 264~303 MB 범위에서 안정, 증가 추세 없음

**즉 8/21 에 보고된 "탭 이동 중 팅김" 은 이 기기·이 빌드에서 재현되지 않았다.**
다만 재현이 안 된 것이지 **없다고 증명된 것은 아니다** — 저사양 기기·장시간 사용·
러닝 3D 진입 등 다른 조건이 남아 있다(아래).

### 아직 안 해 본 조건

- **러닝 3D 모드**(three.js + 카메라 + MediaPipe) — 팅김 주범으로 지목됐던 경로.
  진입하면 "오늘 런닝으로 대체할까요?" 가 뜨고 **실제 루틴이 하루 밀리는** 동작이라
  사용자 계정에서 임의로 실행하지 않았다. 검증하려면 사용자가 직접 하거나 테스트 계정 필요
- 저사양 기기 · 장시간(수십 분) 연속 사용

## 최적화 우선순위

1. 상위 3개 MP4 압축본 제작 및 전송 크기 비교
2. 운동 상세·루틴·플랜의 큰 카탈로그/클라이언트 모듈을 필요한 화면에서만 로드
