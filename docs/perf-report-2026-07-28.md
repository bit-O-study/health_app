0.1~3ms 로 무시할 수준인데, **화면 한 번 여는 데 왕복이 50회 넘게** 일어나고 있었다.

## 2. 원인 — 미들웨어가 "모든 요청"에서 돌고 있었다

화면을 한 번 열면 문서 요청 1개 외에 **프리페치·RSC·스크립트 요청이 20개 가까이**
따라붙는다(하단 탭 6개 프리페치, `sw.js`, `_vercel/insights` …).
이 전부가 미들웨어를 타면서 요청마다:

1. `supabase.auth.getUser()` — GoTrue **HTTP 왕복** (내부적으로 users/sessions/
   identities/mfa_factors/mfa_amr_claims 5개 쿼리)
2. `profiles` 조회(정지/탈퇴/비번변경)
3. `admins` 조회(관리자 판정)

를 했다. 기존에 있던 프리페치 감지(`next-router-prefetch` 헤더)는 **Next 16 에서 그
헤더가 오지 않아 무력**했다(실측: 프리페치 요청 헤더가 전부 `null`, `accept: */*`).

## 3. 적용한 개선

| # | 내용 | 효과 |
| --- | --- | --- |
| 1 | 미들웨어를 **문서(navigation) 요청에서만** 실행 (`accept: text/html` 판정) | 요청당 왕복 3회 × 약 16요청 제거 |
| 2 | `admins` 조회를 **`/admin` 경로에서만** | 일반 페이지 왕복 1회 제거 |
| 3 | matcher 에서 `sw.js`·`_vercel/*` 제외 | 무의미한 미들웨어 실행 제거 |

- **정지 여부(profiles)는 캐시하지 않는다** — 관리자가 정지시키면 즉시 막혀야 한다.
  (60초 캐시를 시도했다가 `admin-ban` E2E 가 깨져서 되돌림 → 정확성 우선.)
- 세션 갱신은 문서 요청 + 페이지 서버 렌더의 supabase 클라이언트가 이어서 한다.

## 4. 남은 비용 (다음 후보, 큰 것부터)

| 순위 | 항목 | 현재 | 개선안 | 예상 |
| --- | --- | ---: | --- | --- |
| 1 | **인증 왕복 4회/화면** | 화면당 4회 (미들웨어 1 + 서버렌더 + 프리페치된 페이지들) | `auth.getUser()` → **`getClaims()`(JWT 로컬 검증)** 로 교체 가능 여부 확인. 비대칭 서명키면 네트워크 0. | 화면당 ~300ms |
| 2 | **프리페치가 대상 페이지를 서버 렌더** | 하단 탭 6개가 백그라운드 렌더(각자 `getCurrentUser`·`group_mode` 등 호출) | 자주 안 쓰는 탭 `prefetch={false}` 또는 정적 셸 | 서버 부하 ↓ (체감 TTFB 는 유지) |
| 3 | `debug_feature_enabled` RPC | 화면당 4회 | 두 플래그를 **한 RPC**로 합치기 | 왕복 2회 |
| 4 | `group_mode()` RPC | 화면당 3회 | 값이 거의 안 바뀜 → 짧은 캐시(`unstable_cache`) | 왕복 2회 |
| 5 | 앱 쿼리 자체 | 0.1~3ms | **최적화 불필요** (인덱스 이미 적정) | — |

## 5. 앱 쿼리 실행시간 (느린 순, 라이브 DB 누적)

DB 실행시간 기준이라 **네트워크 왕복은 미포함**. 상위도 10~30ms 수준이고 대부분
RPC(SECURITY DEFINER 함수) — 인덱스 문제나 풀스캔은 관측되지 않았다.
