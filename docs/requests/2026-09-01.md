## 🛠 작업 (3) — 2.1 운동별 성장 기록

1순위는 남은 게 기기 대기(1.1)·다른 세션(1.2)뿐이라 실행 순서 다음 칸인 2.1 로.

### 먼저 확인한 것 — 데이터는 이미 충분했다
`exercise_completions` 가 완료 시점 스냅샷(운동·기구·세트·횟수·무게·**세트별 기록**)을
갖고 있어서 **새 테이블이 필요 없었다.** 대신 진짜 문제를 찾았다.

### 🔴 찾은 결함 — 집계가 세트별 기록을 안 읽고 있었다
이 앱은 드롭세트·피라미드를 `set_details` 에 저장한다(`SetDetailsEditor` 로 사용자가
직접 넣는다). 그런데 완료 기록 **조회에서 그 컬럼이 빠져 있어**, 성장 그래프도
운동점수도 균일 세트로만 계산하고 있었다.

> 60kg×10 + 50kg×10 + 40kg×12 = 실제 **1,580kg**
> → 예전 계산 3×10×60 = **1,800kg** (14% 과다)

**같은 결함이 두 곳에 있었다** — `progress.ts`(성장 그래프)와 `score.ts`(운동점수 3군데).
한 곳만 고치면 같은 사용자에게 두 화면이 다른 값을 보여 주므로 둘 다 고쳤다.

⚠ **세트별로 기록해 온 사용자는 운동점수가 달라진다**(실제 한 것에 맞게 정정).
균일 세트만 쓰던 사용자는 변화 없음. 되돌릴지 판단이 필요하면 알려주세요.

### 집계 기준을 문서로 못 박음 (`progress.ts` 머리말)
1. 세트별 기록이 있으면 그걸로 센다
2. **단측(한쪽씩) 운동은 볼륨만 ×2** — 사용자는 한쪽 기준으로 적는다.
   **1RM 은 두 배로 안 한다**(한쪽이 든 무게가 그 팔의 능력이다)
3. 맨몸(무게 0)은 볼륨 0 — 볼륨은 "든 무게의 총합"이라 맨몸은 셀 수가 없다

단측 목록(`unilateral-exercises.ts`)에는 **명백한 것만** 넣었다. 런지·스텝업처럼
"10회"가 한쪽인지 합인지 사람마다 다르게 적는 종목은 뺐다 — 틀리게 두 배로 세는 것보다
그대로 두는 게 낫다(한 사람 안에서는 일관되므로 추세는 안 흔들린다).

## 🛠 작업 (4) — 2.2 규칙 기반 점진적 과부하 추천

2.1 에서 "정체 감지·디로드는 2.2 의 일" 이라고 미뤄 둔 걸 이어서 했다.

### 규칙은 넷뿐 — 사용자가 읽고 납득하거나 무시할 수 있어야 한다
1. **목표 횟수를 채웠으면 증량.** 계획이 6회를 시켰고 6회를 했으면 다음엔 올린다
2. **못 채웠으면 같은 무게로 횟수부터.** 무게를 또 올리면 자세가 무너진다
3. **3세션 정체하면 디로드(−10%).** 최고치가 안 늘면 볼륨을 줄이고 다시 올라온다
4. **5세션이면 휴식 권장.** 디로드로도 안 풀렸다는 뜻이다

디로드는 증량보다 **우선**한다 — 목표를 채웠더라도 정체가 더 급한 신호다.

### 보존 정책 — 서버에 파일을 만들지 않는다
만들어 두면 지워야 하고, 지우기 전까지는 링크를 아는 사람이 받을 수 있다. 요청받은
자리에서 DB 를 읽어 **곧바로 응답 본문으로 흘려보내고 끝낸다** — 남는 파일이 없으니
보존 기간을 정할 것도, 지울 것도 없다. (`cache-control: no-store, private`)

### 🔴 스트리밍에서 하루 태울 뻔한 것 — `cookies()` 는 요청 스코프 안에서만
처음엔 조회 계층이 필요할 때 Supabase 클라이언트를 만들었다. 그런데 응답 본문
스트림은 **Response 를 돌려준 뒤에** 돌아간다. 그 시점엔 요청 스코프가 없어
`cookies()` 가 던지고, 헤더(200·Content-Disposition)는 이미 나간 뒤라 사용자에겐
**"다운로드가 중간에 끊김"** 으로만 보인다(E2E 가 `apiRequestContext.get: aborted`
로 잡아 줬다). → 라우트가 **요청 스코프에서 미리 만들어 넘긴다.**

### 대용량 — 전부 제너레이터
내보내기는 화면 조회와 달리 "쓴 기간 전체"를 읽는다. 배열로 모으면 행 수만큼 메모리를
쓰고, 그 함수 인스턴스는 Fluid Compute 라 **다른 요청과 공유된다**. 1,000행씩 읽어
읽는 즉시 내보낸다. 다운로드를 취소하면 `cancel` 에서 제너레이터도 닫는다.

### 한글 인코딩 — 세 군데를 다 챙겨야 안 깨진다
1. **본문**: UTF-8 BOM 을 안 붙이면 엑셀이 CP949 로 읽어 머리글부터 전부 깨진다
2. **파일 이름**: `filename=` 에 한글을 그대로 넣으면 브라우저마다 다르게 깨진다 →
   RFC5987 `filename*=UTF-8''` 로 싣고, 못 읽는 클라이언트용 ASCII 이름을 병기
3. **안드로이드**: `URLUtil.guessFileName` 은 `filename*` 을 못 읽어 ASCII 이름을
   집는다 — 그래서 둘 다 보내는 게 맞다

### 그 밖에 지킨 것
- **CSV 인젝션** — `=`·`+`·`@` 로 시작하는 값은 엑셀이 수식으로 실행한다. 앞에
  작은따옴표를 붙여 글자로 못박되, **숫자로 읽히는 값(-3)은 건드리지 않는다**
- **쉼표·따옴표·줄바꿈** — 음식 이름·메모는 사용자가 쓴 값이라 그대로 들어온다.
  RFC4180 대로 감싸지 않으면 열이 밀린다
- **볼륨은 `recordVolume` 하나로** — 성장 그래프·주간 리포트와 같은 함수를 쓴다.
  여기서 따로 곱하면 화면과 파일이 다른 숫자를 말하게 된다(2.1 에서 겪은 결함)

### 🔴 안드로이드에서 조용히 먹통이던 것
`WebView` 에 `DownloadListener` 가 없으면 첨부파일 응답을 **아무 말 없이 버린다.**
웹에선 되는데 앱에선 버튼이 안 먹는 상태가 됐을 것이다. 시스템 다운로드 관리자로
넘기되 **쿠키를 같이 실어 보낸다**(다운로드 관리자는 별도 프로세스라 세션을 물려받지
못한다 — 안 넣으면 401 짜리 파일이 저장된다). API 28 이하만 저장소 권한을 요청한다.
