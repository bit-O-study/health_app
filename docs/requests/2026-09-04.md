## 🛠 작업 (4) — 남은 확인 2건 파보기 → 🔴 운영 소셜 로그인 장애 발견

둘 다 Supabase **콘솔 설정**이라 코드로는 못 바꾼다(이 레포엔 service_role 키도,
관리 API 토큰(PAT)도, supabase CLI 도 없다 — 있는 건 Postgres 비번뿐인데
GoTrue 설정은 DB 가 아니라 플랫폼 쪽에 있다). 대신 **정확히 뭐가 틀렸는지**를
실측으로 못 박고, 회귀를 잡는 가드를 넣었다.

### 🔴 발견 — 운영에서 구글/카카오 로그인이 실제로 깨져 있다

**우리 콜백 주소가 Supabase 의 Redirect URLs 허용목록에 없다.** 허용목록에 없으면
GoTrue 는 그 주소를 버리고 **Site URL** 로 떨어뜨린다.

실측(가짜 code 로 구글 복귀 지점을 흉내 — 부작용 없음):

```
요청: /auth/v1/callback?state=<진짜 flow state>&code=bogus
결과: 302 → https://health-app-bitostudys-projects.vercel.app/?error=...
기대: https://health-app-five-iota.vercel.app/auth/callback?next=/&native=1
```

**무슨 일이 벌어지나**
1. 사용자가 구글/카카오 인증을 마친다 → 성공.
2. Supabase 가 우리 `/auth/callback` **대신 Site URL 루트**로 보낸다.
3. 루트 페이지엔 code 를 교환하는 코드가 없다 → `exchangeCodeForSession` 이
   **아예 안 돈다** → 세션 없음 → **로그인한 줄 알았는데 로그아웃 상태.**
4. 앱(APK)은 더 나쁘다 — `native=1` 도 같이 버려져 `helssu://` 복귀가 안 되고,
   심지어 **다른 도메인**으로 튄다(앱은 `health-app-five-iota` 를 로드한다).

**왜 9/4 오전 E2E 는 통과했나** — 그 스펙들은 "버튼 → Supabase authorize 로
올바르게 넘기는가"까지만 본다(공급자 동의화면을 자동화할 수 없어서). 깨진 구간은
**공급자가 되돌아온 다음**이라 거기서는 안 잡힌다. 그래서 아래 가드를 따로 만들었다.

   `signUpAndOnboard` 가 온보딩에 도달하지 못한다. → 헬퍼가 가입 후 DB 로 직접
   확인 처리하도록 고쳐야 한다(작업량 있음).
2. **SMTP 를 먼저 봐야 한다.** Supabase 기본 SMTP 는 시간당 2~3통 제한이라,
   커스텀 SMTP 없이 켜면 실사용 가입이 막힌다. (이 앱은 비번찾기 메일을
   Resend/Gmail 로 직접 보내지만, Supabase 확인메일은 별개 설정이다.)
3. 앱 코드는 준비돼 있다 — `!data.session` 분기가 이미 있어 "메일 인증 후 로그인"
   안내로 떨어진다(다만 이 경로엔 테스트가 없다).

**켤지 말지 알려주시면** 1·3 을 맞춰서 작업하겠다.
