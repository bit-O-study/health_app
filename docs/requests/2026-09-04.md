### 🔎 확인 필요 3건 (코드가 아니라 **Supabase 콘솔 설정**)

1. **운영에서 핸드폰 인증이 사실상 항상 건너뛰어진다.**
   `/auth/v1/settings` 가 `phone:false`, `updateUser({phone})` 은
   `500 Unable to get SMS provider` 를 돌려준다. 가입폼은 이 실패를 잡아
   "SMS 설정 전" 안내 후 그냥 통과시키므로 **가입 자체는 정상**이지만,
   전화번호는 아무도 검증하지 않는다. → 정말 인증할 거면 Supabase Auth 의
   Phone 공급자(Twilio) 를 켜야 하고, 안 켤 거면 폼의 "전화번호" 필수 표시를
   빼는 게 맞다. **어느 쪽으로 갈지 결정 필요.**

2. **이메일 확인 없이 가입된다.** `mailer_autoconfirm:true` 라
   `e2e_…@example.com` 같은 없는 주소로도 가입 즉시 로그인된다.
   (편의 vs. 허위계정 — 의도한 설정인지 확인 필요.)

3. **`redirect_to` 허용목록이 열려 있어 보인다.**
   `/auth/v1/authorize?provider=google&redirect_to=https://evil.example.com/x` 가
   그 값을 **그대로 통과**시켰다(정상이면 Site URL 로 치환됨). 앱 코드의
   `safeRedirectPath` 는 내부 경로만 허용해 우리 쪽은 막혀 있지만, Supabase 콘솔
   [Authentication] → [URL Configuration] → Redirect URLs 에 와일드카드가
   들어있을 가능성이 크다. 우리 도메인만 남기는 게 안전.

### 신규 테스트 — `tests/e2e/social-login.spec.ts` (5개)

소셜 로그인은 그동안 **E2E 가 하나도 없었다**(공급자 동의화면을 자동화 못 해서).
동의화면 대신 **우리가 책임지는 구간**만 끊어서 검증한다 — Supabase authorize 요청을
`page.route` 로 가로채 실제 공급자로는 나가지 않는다.

1. 구글 버튼 → `provider=google` + `redirect_to=/auth/callback?next=/` + PKCE(`code_challenge`, `s256`)
2. 카카오 버튼 → `provider=kakao` + 같은 콜백
3. `/login?redirect=/plan` → 콜백 `next=/plan` 로 이어짐
4. ★ 공급자 실패(`/auth/callback?error=…`) → `/login?error=…` 로 사유 노출
5. ★ 앱 콜백(`native=1`) → `helssu://auth/callback` 로 307, `code`·`next` 유지
