## 🛠 작업 (1) — 헬스장 "검색 먼저" 흐름

### 바뀐 흐름

전(前): 이름·주소·기구 60여 개가 **처음부터 한 화면에** 다 떠 있었다. 기구 기본값은
이름을 치기도 전에 이미 "평균 한국 헬스장" 으로 박혀 있었고, 등록된 헬스장을 골라야만
합집합으로 **덮어써졌다**. 즉 **정보가 있는 헬스장인지 알기 전에 기본값이 정해져 있었다.**

후(後): **검색 → 선택 → 기구 확인**.

1. **헬스장 검색** — 이름으로 검색. 결과 한 목록에 우리 DB(회원 있는 곳)와
   카카오 지도(아직 회원 없는 실제 헬스장)가 **같이** 나온다. 회원이 있는 곳은
   `기구 N종` 배지가 붙는다.
2. **선택** — 고르는 순간 **이름·주소가 함께 확정**된다(주소를 따로 칠 일이 없다).
3. **기구 기본값**
   - 그 헬스장 회원이 있으면 → **회원들의 합집합**
     ("이 헬스장 회원들이 등록한 기구를 모아 미리 체크했어요")
   - 아무 정보도 없으면 → **평균 한국 헬스장 기본 보유기구**
     ("아직 등록된 정보가 없어 …")
4. **검색에 안 나오면** → `직접 헬스장 입력하기` 로 **이름+주소**만 손으로.

문구도 요청대로 `헬스장 정보 (선택)` → **`헬스장 검색`**.

### 왜 검색을 한 번에 합쳤나

전에는 DB 검색과 카카오 검색이 **각각 따로** 떠서 목록이 두 개였다. 지도 쪽에서
같은 헬스장을 고르면 **회원 합집합을 못 물려받고** 기본값으로 시작한다 —
같은 지점인데 들어온 문에 따라 결과가 달랐다.

지금은 서버에서 둘을 `Promise.all` 로 동시에 훑고 **한 목록으로 합쳐서** 내려준다.
이름·주소가 같으면 **등록된 쪽만** 남긴다. 주소 없이 등록된 헬스장(직접 입력으로
만들어진 것)은 **이름만 같아도** 같은 곳으로 본다 — 주소를 안 넣은 회원과 지도에서
고른 회원이 갈라지면 **합집합이 두 쪽으로 쪼개진다.**

## 🛠 작업 (3) — 식단 쿼리 최적화

### 먼저 재 본 것 (추측 말고 실측)

라이브 DB에 `EXPLAIN (ANALYZE, BUFFERS)` 를 돌리고 `pg_stat_statements` 를 훑었다.

| 무엇 | 실측 |
|---|---|
| 식단 기록 조회(`food_logs`, 하루치) | **0.39ms** — 인덱스 스캔, 손댈 게 없다 |
| 끼니 사진(`meal_photos`) | 0.04ms |
| 프로필 1행 | 0.35ms |
| **Supabase 왕복 1회(운영)** | **~5ms** — 함수 리전이 DB 와 같은 sin1 이라 이미 싸다 |
| **음식 검색 `search_custom_foods`** | **평균 266ms** (호출 162회) · 최악 **1,870ms** |

🔴 결론이 두 갈래였다. **식단 화면의 지연은 SQL 이 아니라 왕복 수**고,
**진짜 느린 쿼리는 음식 검색**이었다.

### ① 음식 검색 — 1~2글자면 26만 행 전체 스캔이었다

검색은 2단계다. 1단계 접두사(`이름으로 시작`)는 인덱스라 빠르고, 못 채우면
2단계(`이름 중간에 낀 것`, `name ilike '%q%'`)로 채운다. 그런데 이 2단계는
**검색어가 3글자 이상일 때만** trigram GIN 을 탄다 — 앞뒤가 열린 패턴에서 인덱스가
쓸 수 있는 건 온전한 3-gram 뿐이라, 1~2글자에는 뽑을 게 없어 **전체 스캔**이 된다.

한국어 검색어는 한두 글자가 기본이다. 그리고 **1글자 접두사 1,303종 중 756종은
한도(50)를 못 채워 실제로 2단계까지 내려간다** — 드문 경우가 아니라 일상 경로였다.

**고친 것** — 이름에서 1·2글자 조각을 뽑아 GIN 으로 색인(`name_grams` + `custom_foods_name_gram_idx`).
조각으로 후보를 좁힌 뒤 **기존 `ilike` 를 그대로 한 번 더** 걸어 **의미는 안 바꾼다.**

| 검색어 | 전 | 후 |
|---|---|---|
| `김`(1글자) | 224ms | **30ms** |
| `우유` | 220ms | **8.9ms** |
| `자두` | 219ms | **1.2ms** |
| `김치`(최악) | 1,870ms | **5ms 이하** |

재현율 손실 없음(실측 동일): 자두 248/248 · 우유 2,301/2,301 · 라면 807/807.
인덱스 17MB(테이블 41MB). 3글자 이상은 **예전 그대로** trigram 을 탄다.

> ⚠ 처음엔 `word_similarity(%>)` 로 해 봤다(5~12ms). 빠르긴 한데 **단어 경계에서만**
> 맞아서 `저지방우유` 같은 붙은 이름을 놓쳤다(우유 2,301 → 961건). 재현율이 깎이는
> 최적화는 검색을 망가뜨리는 쪽이라 버렸다.

### ② 식단 화면 — 왕복 2회 → 1회

`/diet` 는 프로필을 **먼저 기다린 뒤** 나머지 셋을 병렬로 돌렸다. 프로필은 나머지 조회의
입력이 아닌데(날짜만 있으면 된다) 먼저 기다릴 이유가 없었다 → 넷을 한 묶음으로.

⚠ 효과는 **~5ms** 다. 함수 리전을 DB 와 같은 sin1 로 옮긴 뒤(`b371c32`)라 왕복이 이미
싸다 — 서울(icn1) 시절이었다면 70~90ms 였다. 큰 값은 아니지만, 순차 왕복은 화면마다
쌓이고 리전 한 줄에 따라 언제든 다시 비싸진다.

### ③ RLS — 자기 행을 읽는데 그룹 조인이 행마다 돌았다

허용 정책이 여러 개면 OR 로 합쳐지고 플래너가 순서를 정하는데, 실행계획을 보니
`shares_group_with(user_id)` 가 **먼저** 평가되고 있었다. 자기 식단만 읽는
평범한 조회에서도 **행마다** `group_members` 조인이 돈 것이다.

앞에 싼 비교(`user_id <> (select auth.uid())`)를 둬서 **남의 행일 때만** 함수가 돌게 했다.
`auth.uid()` 도 `(select auth.uid())` 로 감싸 쿼리당 1회(InitPlan)만 평가된다.
**권한 범위는 그대로** — 그룹원 식단 열람 17/17건 그대로 보이는 것 확인했다.
