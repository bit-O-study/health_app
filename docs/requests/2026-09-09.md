## 🛠 작업 (1) — 식단 화면에 남아 있던 왕복 두 개

9/8 작업으로 **서버 안쪽**(SQL·리전)은 정리됐다. 남은 지연은 전부
**브라우저 → 싱가포르(sin1) hop(~80ms)** 쪽이었다. 그 hop 을 두 군데서 줄였다.

### ① 식약처 실시간 조회 — 매 검색 → **빈손일 때만**

검색창은 출처가 셋이다(정적 카탈로그 · `custom_foods` · 식약처 실시간).
예전엔 **검색어마다 셋을 나란히** 불렀다.

🔴 그런데 식약처 API 는 `foodNm` 이 **완전일치**다(9/7 실측: '김치'·'밥'·'닭가슴살'
전부 NODATA). 사용자가 치는 말에는 거의 항상 0건이다 — 즉 대부분의 검색이
**결과가 나오지도 않는 외부 왕복**을 한 번씩 더 태우고 있었다. 화면은 이미 정적·custom
결과로 채워진 채로.

그래서 **앞의 두 출처가 빈손일 때만** 부르게 했다.

- 이 출처가 값을 하는 자리는 "우리 둘 다 모르는 음식"(편의점 도시락·가공식품)이고,
  그건 앞의 둘이 **빈손일 때 정확히 알 수 있다.**
- **AI 한도를 아끼는 원래 목적은 그대로다** — 찾으면 `custom_foods` 에 쌓이고
  다음부터는 우리 DB 에서 나온다.
- 평소 검색에서는 요청이 **아예 사라진다**(3개 → 2개).

`useFoodSearch` 에 `enabled` 스위치를 더했다. 잠긴 동안엔 요청도 안 나가고
`loading` 도 false 다 — true 로 두면 켜지지 않는 출처 때문에 스피너가 영원히 돈다.

### ② 식단 날짜 이동(← →) — 누른 뒤 왕복 → **미리 받아 둠**

`<button onClick={router.push}>` 이었다. 누른 **다음에야** 서버 렌더가 시작되니
한국↔싱가포르 왕복이 그대로 기다리는 시간이었다.

→ **`<Link prefetch>`** 로 바꿨다. 화면에 보이는 순간 어제/내일을 미리 받아 둔다.

🔴 **`prefetch` 를 빠뜨리면 아무 소용이 없다.** 동적 라우트는 기본이
`staleTimes.dynamic = 0초` 라 받아 두자마자 낡은 것으로 처리된다.
`prefetch`(=true)여야 `staleTimes.static`(기본 5분)이 적용돼 실제로 재사용된다.
(저장·삭제 뒤 `router.refresh()` 가 이 캐시도 같이 무효화하므로 낡은 값이 남지 않는다.)

- 오늘이면 '다음 날'은 주소가 없으니 그대로 비활성 버튼.
- 저장 중(`pending`)에는 옛 `disabled` 와 똑같이 막는다(낙관적 상태 보호).
- ⚠ 대가: 식단을 열 때마다 **어제 페이지가 한 번 더 서버 렌더**된다(과거 날짜면 2개).
  쿼리 4개 × ~5ms 짜리라 감당되는 값이라고 봤다.

## 🛠 작업 (3) — 트레이너 대시보드

B2B(트레이너/헬스장)의 첫 칸. **새 개념을 만들지 않고 기존 그룹을 그대로 쓴다** —
`groups.owner_id` 가 이미 있으니 **그룹장 = 트레이너**, 그룹원 = 담당 회원이다.
초대 링크·멤버 관리·이름 규칙이 전부 이미 돌아가고 있어서 새로 만들 게 없었다.

들어가는 문: 그룹 화면의 그룹장 전용 **`회원 관리`** 버튼 → `/groups/<id>/trainer`.

### 화면이 답하는 질문 — "오늘 누구에게 연락할까"

회원별로 이번 주 **운동일수 / 목표일수 · 식단 기록일수 · 마지막 운동일 · 체중 변화**,
그리고 챙겨야 할 이유를 한 줄씩.

🔴 **랭킹과 정렬 방향이 반대다.** 그룹 랭킹은 잘한 사람이 위로 온다(경쟁이 목적).
트레이너 화면은 **처지는 사람이 위로** 온다 — 트레이너가 이 화면을 여는 이유는 1등을
보려는 게 아니라 연락할 사람을 찾는 것이다. 잘하는 회원이 위에 쌓이면 정작 챙겨야 할
사람이 스크롤 아래로 밀린다.

판정에서 신경 쓴 것:

- **"아직 기록이 없다" 와 "요즘 안 한다" 를 나눈다.** 가입만 하고 한 번도 안 한 회원은
  이탈이 아니라 **온보딩 실패**다 — 트레이너가 할 말이 완전히 다르다.
- **목표 미설정은 0% 가 아니다.** 0% 로 만들면 루틴을 아직 안 짠 신규 회원이
  '최악의 회원'으로 맨 위에 뜬다.
- **체중은 방향을 판단하지 않는다.** 증량이 목표인 회원도 있다 — ±2kg 이상 '변화'만 알린다.
- 3일 미만 공백은 조용하다(주 3회 회원도 이틀은 정상).
- 급한 정도가 같으면 이름순 — 볼 때마다 순서가 바뀌면 "어제 본 그 회원"을 못 찾는다.

### 🔴 권한 — RLS 를 넓히지 않고 SECURITY DEFINER 함수로

필요한 값 중 **`user_routines`(주간 목표)·`weight_logs`(체중 추이)는 그룹원에게 열려
있지 않다.** 이걸 "그룹원이면 읽기" 정책으로 열면 트레이너뿐 아니라 **같은 그룹의 모든
사람**이 남의 체중 이력을 보게 된다 — 이 앱의 그룹은 친구 모임이기도 하다.

그래서 `trainer_board(group_id, from, to)` 안에서 `groups.owner_id = auth.uid()` 를
직접 확인한다. 아니면 조용히 빈 결과다. 화면 쪽에서도 한 번 더 확인해 **아예 안 그린다**
(함수만 믿으면 회원 없는 그룹에서 빈 대시보드가 그려져 "열린다"는 오해를 준다).

집계는 **한 문장**이다. 회원마다 따로 물으면 회원 수만큼 왕복이 느는데, 트레이너 화면은
회원이 많을수록 값이 커지는 화면이라 그 반대로 굴면 안 된다.

주간 목표일수는 `splits`(N분할)가 0 이어도 `custom_week` 에서 휴식이 아닌 날을 센다 —
직접 짠 사용자의 목표가 0 이면 달성률이 항상 0% 가 된다(실측: 루틴 18개 중 7개가 splits=0).

## 🛠 작업 (4) — 트레이너가 회원에게 루틴 배정

트레이너 대시보드의 회원 카드에 **`루틴 배정`** → `/groups/<id>/trainer/assign/<회원>`.
내 루틴의 한 일차를 골라 회원의 한 일차로 옮겨 담는다.

이미 있는 **소개 루틴 담기**(`applyRoutineShareAction`)와 같은 모양이다. 다른 점은
**쓰는 대상이 남**이라는 것뿐이라, 그 규칙들을 그대로 가져왔다.

### 규칙 세 가지 (전부 이유가 있다)

🔴 **무게는 넘기지 않는다.** 트레이너의 100kg 스쿼트가 초보 회원 화면에 그대로 박히면
위험하고, 애초에 남의 신체 수치다. 회원이 운동하며 자기 무게를 넣는다.
(`routine_shares` 에 `include_weights` 가 있는 이유와 같다.) `set_details` 도 같이 비운다.

🔴 **부위는 받는 쪽으로 통일한다.** 원본 부위를 그대로 쓰면 회원 루틴에 없는 부위의
운동이 생겨 **어느 화면에도 안 뜬다** — 소개 루틴 담기에서 이미 겪은 문제다.
부위 계산은 TS(`routineDaySlots`)가 하고 SQL 로 넘긴다. 그 규칙을 SQL 에 다시 구현하면
트레이너가 보는 부위와 회원이 보는 부위가 갈린다.

🔴 **한 번에 안 끝난다.** 회원이 그 일차에 짜 둔 운동은 지워지는, 되돌리기 어려운
작업이다. "누구의 무슨 요일이 어떻게 바뀌는지"를 문장으로 보여 준 뒤 확인을 받는다 —
회원 입장에서는 **자기가 안 한 변경**이라, 무엇이 바뀌었는지 말할 수 있어야 한다.

### 권한

`trainer_assign_routine_day` 도 SECURITY DEFINER 다. 남의 `routine_exercises` 를 쓰는
일이라 RLS 로는 안 된다. 안에서 **그룹장인지 + 대상이 그 그룹 회원인지**를 확인하고,
아니면 `-1`(아무 일도 안 함). **자기 자신에게도 못 한다** — 트레이너 루틴이 자기 루틴을
덮어쓰는 사고를 막는다.

배정 화면이 회원의 일차 목록을 그리려면 회원 `user_routines` 가 필요한데 그것도 그룹원에게
안 열려 있어 `trainer_member_routine` 으로 받는다(같은 그룹장 확인).

## 🛠 작업 (5) — 배정 알림 (회원이 모르고 바뀌던 구멍)

작업 (4)의 남은 구멍. **회원은 자기 루틴이 바뀐 걸 몰랐다** — 어느 날 운동 목록이
달라져 있는데 원인을 알 방법이 없다(앱 버그로 읽힌다). 자기가 안 한 변경이라
알림이 있어야 기능이 완성된다.

배정 성공 뒤 회원에게: **"루틴이 바뀌었어요 / OO님이 5일 · 등 운동을 새로 짜 줬어요"**
(누르면 `/routine`).

### 🔴 새 알림 종류를 더할 때 조용히 빠지는 자리가 넷이었다

전부 **화면에는 아무 이상이 없는** 자리다.

1. `NOTIFICATION_KINDS` — 빠지면 설정 화면에 스위치가 안 생긴다
2. `PUSH_TYPE_TO_KIND` — 빠지면 **설정에서 못 끄는 알림**이 된다
3. `notification_preferences` 컬럼 — 없으면 저장이 안 된다
4. **조회 컬럼 목록** — 문자열로 따로 적혀 있어서, 종류를 더해도 그 컬럼만 안 읽히고
   **꺼도 알림이 그대로 나간다**

4번은 아예 못 틀리게 바꿨다. `PREFERENCE_COLUMNS` 를 손으로 적지 않고

안 그러면 설정 화면의 스위치가 조용히 장식이 된다. 방해 금지(기본 22~07)도 함께 지킨다.
알림 실패는 삼킨다 — 배정은 이미 됐고, 알림 때문에 되돌릴 일은 아니다.

## 🛠 작업 (6) — 트레이너가 회원에게 코멘트

회원 카드 → **`코멘트`** → `/groups/<id>/trainer/comment/<회원>`.
남기면 회원의 **오늘의 운동 화면 위쪽**에 뜨고, 알림도 간다.

그룹 응원(`group_cheers`)과 다르다: 응원은 **10자·하루 한 문구·그룹원 누구나**라
"화이팅" 용이고, 이건 **500자·여러 개·트레이너만**이라 자세를 짚어 줄 수 있다.

### 🔴 RLS 정책에 구멍이 있었다 (실측으로 뚫림)

처음 쓴 정책은 이랬다:

```sql
and exists (select 1 from public.group_members m
             where m.group_id = group_id and m.user_id = member_id)
```

`m.group_id = group_id` 의 오른쪽 `group_id` 가 **서브쿼리의 컬럼**으로 붙는다 —
`m.group_id = m.group_id`, 즉 **항상 참**이다. 결과: **아무 그룹에나 속한 사람이면
누구에게든 코멘트를 남길 수 있었다.**

라이브에서 직접 넣어 보고 알았다(그룹 밖 사람에게 insert 가 성공했다).
바깥 행을 **표 이름으로 못 박아** 고쳤다(`trainer_comments.group_id`).

이걸 잡는 테스트는 **다른 그룹에 속한 사람**으로 검사해야 한다 — 아무 그룹에도 없는
사람으로 검사하면 뚫린 정책도 통과해 버려서 가드가 아무것도 안 지킨다.

### 여기는 SECURITY DEFINER 가 필요 없다

`trainer_board` 와 달리, 필요한 판단(그룹장인가·그 그룹 회원인가)이 전부 **자기 행의
컬럼**으로 표현된다 → RLS 한 곳에서 끝난다. 서버 액션은 길이만 본다.
같은 규칙을 액션에도 두면 한쪽만 고쳐지는 날이 온다(소스 가드 테스트로 못 박음).

읽기는 **당사자 둘만**(회원 본인·쓴 트레이너). 같은 그룹의 다른 회원에게도 안 보인다 —
자세 지적은 남 앞에서 할 말이 아니다. 회원은 받은 코멘트를 **지우거나 고칠 수 없다**
(update 정책 자체를 안 만들었다 — 있으면 트레이너 말을 회원이 바꿔 쓸 수 있다).

### 🔴 회원이 볼 자리가 없으면 없는 기능이다

알림은 놓치면 끝이고 끌 수도 있다. 트레이너 화면은 회원이 못 본다.
그래서 **오늘의 운동 화면**에 카드로 띄운다 — 자세 지적은 운동 직전에 읽어야 쓸모가 있다.
코멘트가 없으면 아무것도 안 그린다. 조회는 기존 `Promise.all` 묶음에 실어 왕복을 안 늘렸다.

### 곁다리로 잡은 실제 버그

코멘트를 남겨도 **목록에 안 붙었다.** 목록이 서버 prop 으로 초기화한 로컬 상태라
`router.refresh()` 로 서버가 다시 그려도 `useState(initial)` 은 안 바뀐다.
→ 액션이 만든 행을 돌려주고 화면이 앞에 붙인다. (E2E 가 이걸 잡았다.)

|---|---|

## 🛠 작업 (7) — B2B 과금 (팀 요금제)

트레이너·헬스장이 내면 **그 그룹 회원 전원이 프리미엄**. 회원은 따로 결제하지 않는다.

### 🔴 구글 플레이 결제를 쓰지 않는다

Play 인앱결제는 **개인용**이다. 사업자는 비용 처리를 해야 해서 **세금계산서·계좌이체**가
필요하고, 앱 안에서 외부결제로 유도하면 Play 정책 위반이다. 그래서 개인 구독(Play)과
**나란히 다른 길**을 냈다 — 둘 중 하나만 살아 있어도 프리미엄이다.

흐름: 그룹장이 신청 → 입금 → **관리자가 확인하고 기간을 넣는다**.
입금을 코드가 확인할 방법이 없어서 **일부러 사람이 승인한다.** 자동 승인을 붙이면
신청만으로 프리미엄이 새어 나간다.

### 권한이 뚫리면 결제가 무의미하다

- 신청(insert)은 **그룹장이 `requested` 로만**. 서버 액션은 아예 `status` 를 인자로
  안 받는다 — 화면 흉내만으로 스스로 `active` 가 되면 안 된다(막을 게 없으면 뚫릴 것도 없다).
- 승인(active 로 바꾸기)은 **관리자만**. RLS + 서버 액션 양쪽에서 본다.
- 신청 내역(금액·사업자정보)은 **그룹장·관리자만** 본다. 같은 그룹 회원에게도 안 보인다.
- 🔴 권한은 status 가 아니라 **period_end** 에서 나온다(개인 구독과 같은 규칙).
  만료 처리를 깜빡한 행 하나가 그 팀 전원을 계속 프리미엄으로 만들면 안 된다.

⚠ 이 가드를 짜다 **테스트가 먼저 틀렸다.** 검사 계정으로 관리자를 뽑는 바람에
`is_admin()` 정책이 통과해 "그룹장이 자가승인된다"는 오탐이 났다. 정책은 멀쩡했다.
→ 테스트가 관리자를 제외하고 뽑도록 고쳤고, 그 이유를 파일 머리말에 적어 뒀다.

### 요금제 (안내가 — 실제 청구는 승인할 때 사람이 넣는다)

| | 월 | 기준 |
|---|---|---|
| 트레이너 | 39,000원 | 회원 15명까지 |
| 헬스장 | 149,000원 | 인원 제한 없음 |

부가세 별도. 신청서의 요금제를 그대로 승인하지 않고 **금액·기간·인원을 관리자가
넣는다** — 실제 청구는 협의로 달라지는데 신청값을 그대로 쓰면 장부와 갈린다.

## 🛠 작업 (8) — 입금 계좌 안내 (관리자 설정)

작업 (7)에서 계좌번호를 코드에 안 박고 남겨 둔 자리. 이제 **관리자 설정 → 입금 계좌
안내**에서 은행·계좌번호·예금주·안내문구를 넣으면, 팀 요금제를 **신청한 그룹장**의
화면에 그대로 뜬다.

### 🔴 왜 코드가 아니라 설정인가

계좌는 바뀐다(은행 변경·법인 전환). 바꿀 때마다 배포해야 하면 결국 안 바꾸고,
그러면 **사용자가 없는 계좌로 입금한다.** 그게 제일 나쁜 실패다.

### 🔴 셋 다 채워야 뜬다

은행·계좌번호·예금주 중 하나라도 비면 **아무것도 안 띄우고** "확인되면 연락드릴게요"로
남는다. 반쯤 채운 계좌 안내는 없는 것보다 나쁘다 — 입금하다 만다.
관리자 화면이 지금 상태를 그대로 알려 준다("지금은 안 보임") — 안 그러면
"저장했는데 왜 신청자에게 안 보이지"로 헤맨다.

### app_settings 를 통째로 열지 않았다

`app_settings` 는 **관리자 전용 RLS** 라 트레이너가 직접 못 읽는다. 그룹탭 모드

(`billing_deposit_info()`)를 뒀다. 표를 열면 디버그 계정 목록 같은 다른 설정까지

## 🛠 작업 (9) — 전수 조사에서 나온 것 (고친 것 + 남은 것)

### 🔴 고친 것 1 — 내가 만든 링크가 아무 데도 안 갔다

## 🛠 작업 (10) — 조사에서 남겨 뒀던 것들

### ① 추천글 **제목 자동 채움**에서 일차 제거

루틴 소개글을 쓰면 제목이 `1일차 · 가슴 · 삼두` 로 자동으로 채워졌다 → `가슴 · 삼두`.

🔴 **"1일차" 는 쓰는 사람의 루틴에서만 뜻이 있다.** 읽는 사람에게 내 3일차가 무슨 날인지
알 방법이 없다(남의 3일차와 같을 이유가 없다). 그래서 **고르는 자리와 남에게 보이는
자리를 나눴다** — 일차 선택 시트에는 `1일차 · 가슴` 그대로(몇 일차인지가 정보다),
제목 기본값에는 부위만.

### ② 익명(anon) 실행 권한 정리

🔴 Supabase 는 public 스키마 함수에 **anon 실행권한을 기본으로 준다.** 로그인해야만
쓰는 기능 6개를 회수했다.

⚠ **`revoke ... from anon` 만으로는 안 빠진다.** 기본 권한은 `PUBLIC` 에 붙어 있어
anon 이 PUBLIC 을 통해 계속 부른다(실측으로 확인 — 처음에 그렇게 해서 하나만 빠졌다).
PUBLIC 에서 회수한 뒤 `authenticated` 에게 **명시적으로 다시 줘야** 한다. 안 그러면
로그인 사용자까지 막힌다.

| 회수 | |
|---|---|
| `bump_routine_share_saves` · `consume_ai_quota` · `join_group_by_token` · `debug_feature_enabled` · `is_debug_account` | anon 차단, 로그인 사용자는 그대로 |
| `rls_auto_enable` | **유지보수용** — 로그인 사용자도 차단(소유자만) |

🔴 **회수하면 안 되는 것들**을 이유와 함께 테스트에 못 박았다:
- 로그인 **전** 흐름: `find_login_email` · `request_password_otp` ·
  `verify_otp_and_reset` · `group_name_by_token` · `consume_rate_limit`
- **RLS 정책이 부른다**(정책 식은 조회자 권한으로 평가 → 회수하면 비로그인 조회가
  통째로 오류): `is_admin` · `is_group_member` · `is_post_moderator` ·
  `shares_group_with` · `can_see_community_post`
- `/community`·`/groups` 는 보호 경로가 아니라 비로그인도 닿는다 →
  `community_post_counts` · `teaching_post_counts` · `group_mode` 도 유지

자매앱 함수 `iq_*`(관리자 통계 포함)는 **이 저장소가 안 쓴다** — 그쪽에서 판단할 일이라
안 건드렸다. 아이큐 앱 저장소에서 `iq_admin_stats`·`iq_recent_results`·
`iq_grade_distribution` 의 anon 권한은 한 번 보시는 게 좋겠다.

### ③ 테스트 격리 — 원인은 '청소'였다

`rate-limit-guard` 가 **E2E 와 같이 돌리면만** 깨지던 이유를 찾았다.
`consume_rate_limit` 은 호출마다 **1% 확률로 "하루 지난 창"을 청소**하는데,
테스트가 **2025-09 고정 창**을 쓰고 있었다 → 다른 트래픽이 그 청소를 트리거하면
검사 중인 행이 지워진다. 단독 실행에선 호출이 적어 안 걸렸다.

→ 창을 **지금 시각**으로 잡게 고쳤다. **BE 전체와 E2E 를 동시에 돌려 확인**했다
(187파일 1,932개 green + 식단 E2E 3개 통과).
