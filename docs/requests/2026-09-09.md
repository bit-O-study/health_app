## 🛠 작업 (1) — 식단 화면에 남아 있던 왕복 두 개

9/8 작업으로 **서버 안쪽**(SQL·리전)은 정리됐다. 남은 지연은 전부
**브라우저 → 싱가포르(sin1) hop(~80ms)** 쪽이었다. 그 hop 을 두 군데서 줄였다.

### ① 식약처 실시간 조회 — 매 검색 → **빈손일 때만**

검색창은 출처가 셋이다(정적 카탈로그 · `custom_foods` · 식약처 실시간).
예전엔 **검색어마다 셋을 나란히** 불렀다.

🔴 그런데 식약처 API 는 `foodNm` 이 **완전일치**다(9/7 실측: '김치'·'밥'·'닭가슴살'
전부 NODATA). 사용자가 치는 말에는 거의 항상 0건이다 — 즉 대부분의 검색이
**결과가 나오지도 않는 외부 왕복**을 한 번씩 더 태우고 있었다. 화면은 이미 정적·custom
결과로 채워진 채로.

그래서 **앞의 두 출처가 빈손일 때만** 부르게 했다.

- 이 출처가 값을 하는 자리는 "우리 둘 다 모르는 음식"(편의점 도시락·가공식품)이고,
  그건 앞의 둘이 **빈손일 때 정확히 알 수 있다.**
- **AI 한도를 아끼는 원래 목적은 그대로다** — 찾으면 `custom_foods` 에 쌓이고
  다음부터는 우리 DB 에서 나온다.
- 평소 검색에서는 요청이 **아예 사라진다**(3개 → 2개).

`useFoodSearch` 에 `enabled` 스위치를 더했다. 잠긴 동안엔 요청도 안 나가고
`loading` 도 false 다 — true 로 두면 켜지지 않는 출처 때문에 스피너가 영원히 돈다.

### ② 식단 날짜 이동(← →) — 누른 뒤 왕복 → **미리 받아 둠**

`<button onClick={router.push}>` 이었다. 누른 **다음에야** 서버 렌더가 시작되니
한국↔싱가포르 왕복이 그대로 기다리는 시간이었다.

→ **`<Link prefetch>`** 로 바꿨다. 화면에 보이는 순간 어제/내일을 미리 받아 둔다.

🔴 **`prefetch` 를 빠뜨리면 아무 소용이 없다.** 동적 라우트는 기본이
`staleTimes.dynamic = 0초` 라 받아 두자마자 낡은 것으로 처리된다.
`prefetch`(=true)여야 `staleTimes.static`(기본 5분)이 적용돼 실제로 재사용된다.
(저장·삭제 뒤 `router.refresh()` 가 이 캐시도 같이 무효화하므로 낡은 값이 남지 않는다.)

- 오늘이면 '다음 날'은 주소가 없으니 그대로 비활성 버튼.
- 저장 중(`pending`)에는 옛 `disabled` 와 똑같이 막는다(낙관적 상태 보호).
- ⚠ 대가: 식단을 열 때마다 **어제 페이지가 한 번 더 서버 렌더**된다(과거 날짜면 2개).
  쿼리 4개 × ~5ms 짜리라 감당되는 값이라고 봤다.

## 🛠 작업 (3) — 트레이너 대시보드

B2B(트레이너/헬스장)의 첫 칸. **새 개념을 만들지 않고 기존 그룹을 그대로 쓴다** —
`groups.owner_id` 가 이미 있으니 **그룹장 = 트레이너**, 그룹원 = 담당 회원이다.
초대 링크·멤버 관리·이름 규칙이 전부 이미 돌아가고 있어서 새로 만들 게 없었다.

들어가는 문: 그룹 화면의 그룹장 전용 **`회원 관리`** 버튼 → `/groups/<id>/trainer`.

### 화면이 답하는 질문 — "오늘 누구에게 연락할까"

회원별로 이번 주 **운동일수 / 목표일수 · 식단 기록일수 · 마지막 운동일 · 체중 변화**,
그리고 챙겨야 할 이유를 한 줄씩.

🔴 **랭킹과 정렬 방향이 반대다.** 그룹 랭킹은 잘한 사람이 위로 온다(경쟁이 목적).
트레이너 화면은 **처지는 사람이 위로** 온다 — 트레이너가 이 화면을 여는 이유는 1등을
보려는 게 아니라 연락할 사람을 찾는 것이다. 잘하는 회원이 위에 쌓이면 정작 챙겨야 할
사람이 스크롤 아래로 밀린다.

판정에서 신경 쓴 것:

- **"아직 기록이 없다" 와 "요즘 안 한다" 를 나눈다.** 가입만 하고 한 번도 안 한 회원은
  이탈이 아니라 **온보딩 실패**다 — 트레이너가 할 말이 완전히 다르다.
- **목표 미설정은 0% 가 아니다.** 0% 로 만들면 루틴을 아직 안 짠 신규 회원이
  '최악의 회원'으로 맨 위에 뜬다.
- **체중은 방향을 판단하지 않는다.** 증량이 목표인 회원도 있다 — ±2kg 이상 '변화'만 알린다.
- 3일 미만 공백은 조용하다(주 3회 회원도 이틀은 정상).
- 급한 정도가 같으면 이름순 — 볼 때마다 순서가 바뀌면 "어제 본 그 회원"을 못 찾는다.

### 🔴 권한 — RLS 를 넓히지 않고 SECURITY DEFINER 함수로

필요한 값 중 **`user_routines`(주간 목표)·`weight_logs`(체중 추이)는 그룹원에게 열려
있지 않다.** 이걸 "그룹원이면 읽기" 정책으로 열면 트레이너뿐 아니라 **같은 그룹의 모든
사람**이 남의 체중 이력을 보게 된다 — 이 앱의 그룹은 친구 모임이기도 하다.

그래서 `trainer_board(group_id, from, to)` 안에서 `groups.owner_id = auth.uid()` 를
직접 확인한다. 아니면 조용히 빈 결과다. 화면 쪽에서도 한 번 더 확인해 **아예 안 그린다**
(함수만 믿으면 회원 없는 그룹에서 빈 대시보드가 그려져 "열린다"는 오해를 준다).

집계는 **한 문장**이다. 회원마다 따로 물으면 회원 수만큼 왕복이 느는데, 트레이너 화면은
회원이 많을수록 값이 커지는 화면이라 그 반대로 굴면 안 된다.

직접 짠 사용자의 목표가 0 이면 달성률이 항상 0% 가 된다(실측: 루틴 18개 중 7개가 splits=0).

## 🛠 작업 (4) — 트레이너가 회원에게 루틴 배정

트레이너 대시보드의 회원 카드에 **`루틴 배정`** → `/groups/<id>/trainer/assign/<회원>`.
내 루틴의 한 일차를 골라 회원의 한 일차로 옮겨 담는다.

이미 있는 **소개 루틴 담기**(`applyRoutineShareAction`)와 같은 모양이다. 다른 점은
**쓰는 대상이 남**이라는 것뿐이라, 그 규칙들을 그대로 가져왔다.

### 규칙 세 가지 (전부 이유가 있다)

🔴 **무게는 넘기지 않는다.** 트레이너의 100kg 스쿼트가 초보 회원 화면에 그대로 박히면
위험하고, 애초에 남의 신체 수치다. 회원이 운동하며 자기 무게를 넣는다.
(`routine_shares` 에 `include_weights` 가 있는 이유와 같다.) `set_details` 도 같이 비운다.

🔴 **부위는 받는 쪽으로 통일한다.** 원본 부위를 그대로 쓰면 회원 루틴에 없는 부위의
운동이 생겨 **어느 화면에도 안 뜬다** — 소개 루틴 담기에서 이미 겪은 문제다.
부위 계산은 TS(`routineDaySlots`)가 하고 SQL 로 넘긴다. 그 규칙을 SQL 에 다시 구현하면
트레이너가 보는 부위와 회원이 보는 부위가 갈린다.

🔴 **한 번에 안 끝난다.** 회원이 그 일차에 짜 둔 운동은 지워지는, 되돌리기 어려운
작업이다. "누구의 무슨 요일이 어떻게 바뀌는지"를 문장으로 보여 준 뒤 확인을 받는다 —
회원 입장에서는 **자기가 안 한 변경**이라, 무엇이 바뀌었는지 말할 수 있어야 한다.

### 권한

`trainer_assign_routine_day` 도 SECURITY DEFINER 다. 남의 `routine_exercises` 를 쓰는
일이라 RLS 로는 안 된다. 안에서 **그룹장인지 + 대상이 그 그룹 회원인지**를 확인하고,
아니면 `-1`(아무 일도 안 함). **자기 자신에게도 못 한다** — 트레이너 루틴이 자기 루틴을
덮어쓰는 사고를 막는다.

배정 화면이 회원의 일차 목록을 그리려면 회원 `user_routines` 가 필요한데 그것도 그룹원에게
안 열려 있어 `trainer_member_routine` 으로 받는다(같은 그룹장 확인).

  쓰기**다. 권한이 새면 아무나 남의 루틴을 지울 수 있는데, 당한 사람은 자기가 안 한
