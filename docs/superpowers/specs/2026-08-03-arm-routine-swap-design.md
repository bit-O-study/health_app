# 팔 루틴 일차 간 교환 Design

## Goal

운동 등록 화면에서 `등 + 팔`, `어깨 + 팔`처럼 여러 일차에 팔 슬롯이 있을 때, 사용자가 두 일차의 팔 루틴 전체를 안전하게 교환할 수 있게 한다.

사용자에게는 팔 관련 배지를 `팔`로 통합해 보여주되, 이두·삼두 구분은 운동 추천과 직접 추가 필터를 위해 내부 데이터로 유지한다.

## Current Behavior and Root Cause

- 커스텀 루틴은 `custom_week`에 `arm`, `biceps`, `triceps` 같은 블록 ID를 저장한다.
- `routineDaySlots`는 이 블록들을 내부 `focus: "arm"` 슬롯으로 묶되 `blockIds`에는 원래 선택값을 유지한다.
- 개별 운동 행은 `majorMuscleTag()`를 사용해 이두·삼두 운동도 첫 배지가 `팔`로 표시된다.
- 반면 일차 상단과 운동 추가 메뉴는 슬롯 라벨을 사용해 `이두` 또는 `삼두`로 표시될 수 있어 표기가 일관되지 않다.
- 같은 팔 슬롯이 여러 일차에 있어도 해당 일차들의 운동 목록을 교환하는 기능은 없다.

## Product Decisions

1. 이번 기능은 커스텀 루틴의 팔 슬롯 교환만 지원한다.
2. 운동 등록 화면에서는 모든 팔 계열 슬롯을 `팔`로 표시한다.
3. 루틴 설정 화면에서는 이두·삼두 선택을 계속 제공하며 내부 `blockIds`를 보존한다.
4. 교환 단위는 운동 목록과 내부 팔 블록 지정이 결합된 팔 슬롯 전체다.
5. 워밍업·마무리, 오늘만 변경 데이터, 과거 완료 기록은 교환하지 않는다.
6. 팔 슬롯이 두 개 이상 있을 때만 교환 기능을 노출한다.

## User Experience

### Entry and Target Selection

교환 가능한 다른 팔 일차가 있으면 해당 일차 카드에 `팔 루틴 교환` 버튼을 표시한다.

```text
1일차  등 · 팔                     [팔 루틴 교환]
2일차  어깨 · 팔
```

버튼을 누르면 현재 일차를 제외한 팔 슬롯 일차만 대상으로 표시한다.

```text
교환할 일차  [2일차 · 어깨 + 팔] [4일차 · 가슴 + 팔]
```

대상을 선택하면 다음 내용을 확인받는다.

```text
1일차 팔 루틴과 2일차 팔 루틴을 교환할까요?
운동 목록과 내부 이두·삼두 설정이 함께 이동합니다.
```

성공 후 화면을 다시 불러와 운동 목록과 운동 추가 필터를 새 슬롯 데이터에 맞춘다.

### Unsaved Changes

화면의 어느 운동 슬롯이든 저장하지 않은 변경이 있으면 교환하지 않는다. 성공 후
하드 새로고침 과정에서 관련 없는 부위의 로컬 편집까지 유실되는 일을 막기 위한
안전 규칙이다.

```text
저장하지 않은 운동 변경이 있습니다. 먼저 각 일차를 저장해주세요.
```

### Pending and Failure

- 요청 중에는 모든 팔 교환 버튼을 비활성화해 중복 교환을 막는다.
- 성공 전까지 클라이언트 운동 목록을 낙관적으로 바꾸지 않는다.
- 실패하면 현재 화면을 유지하고 오류 메시지를 표시한다.

## Display and Slot Rules

운동 등록 화면에 한해 `focus === "arm"`인 슬롯 라벨은 항상 `팔`로 표시한다.

- `["arm"]` → `팔`
- `["biceps"]` → `팔`
- `["triceps"]` → `팔`
- `["biceps", "triceps"]` → `팔`

운동 선택과 추천 목록은 기존처럼 `blockIds`를 사용하므로 이두·삼두 운동은 섞이지 않는다.

교환 시 한 일차의 팔 계열 블록 전체를 하나의 묶음으로 취급한다. 팔이 아닌 블록의 값과 순서는 유지한다.

```text
before
1일차: [back, biceps]
2일차: [shoulder, triceps]

after
1일차: [back, triceps]
2일차: [shoulder, biceps]
```

교환 결과가 일차당 최대 3개 블록 제한을 넘는 대상은 선택지에서 제외하고 서버에서도 거부한다.

## Data Integrity Architecture

### No Existing-Data Migration

- 기존 `routine_exercises` 행을 일괄 수정하거나 백필하지 않는다.
- 테이블 컬럼과 기존 데이터 형식은 변경하지 않는다.
- 교환용 트랜잭션 함수만 `supabase/schema.sql`에 추가한다.

### Preserve Row Identity

운동 행을 삭제하거나 다시 만들지 않는다. 선택한 두 일차의 `focus = "arm"` 행은 UUID를 유지하고 `day_index`만 서로 바꾼다.

다음 값은 그대로 보존된다.

- 운동 행 ID
- 운동 ID와 기구
- 순서
- 세트·횟수·무게
- 세트별 설정
- 메모
- 생성 시각
- 과거 완료 기록이 참조하는 행 ID

### Atomic Database Transaction

서버 액션은 검증된 요청을 Postgres RPC 한 번으로 전달한다. RPC는 한 트랜잭션에서 다음을 수행한다.

1. 로그인 사용자의 `user_routines` 행을 잠근다.
2. 현재 `custom_week`가 화면의 예상 스냅샷과 같은지 확인한다.
3. 서로 다른 두 일차가 모두 팔 슬롯을 포함하는지 확인한다.
4. 다음 `custom_week`가 7일 구조와 일차당 최대 3개 블록 제한을 지키는지 확인한다.
5. 두 일차의 `focus = "arm"` 행을 단일 `CASE` 업데이트로 교환한다.
6. `user_routines.custom_week`를 다음 값으로 갱신한다.

검증 실패나 SQL 오류가 발생하면 함수 전체가 롤백되므로 운동 행과 `custom_week` 중 한쪽만 바뀐 상태가 남지 않는다.

RPC는 `SECURITY INVOKER`와 `auth.uid()`를 사용해 로그인 사용자의 데이터만 수정한다. 서버 액션도 현재 루틴과 입력을 별도로 검증한다.

### Concurrency

RPC는 사용자 루틴 행을 잠그고 예상 `custom_week`를 비교한다. 다른 탭에서 루틴이 먼저 변경됐으면 오래된 화면의 요청을 거부하고 새로고침을 안내한다.

## Responsibilities

### Server

- 로그인과 커스텀 루틴 여부 확인
- 일차 범위와 서로 다른 일차인지 확인
- 두 일차의 팔 블록 추출
- 교환 후 `custom_week` 계산과 최대 블록 수 검증
- 원자적 RPC 호출
- 성공 시 `/plan`, `/routine`, `/settings/routine` 재검증

### Client

- 팔 슬롯이 반복되는 일차만 교환 UI 제공
- 현재 일차와 블록 제한을 넘기는 대상을 제외
- 화면 전체의 미저장 상태 검사
- 확인, pending, error 상태 표시
- 성공 후 하드 새로고침으로 `plans`와 `blockIds`를 함께 재동기화

## Error Handling

- 로그인 만료: `로그인이 필요합니다.`
- 오래된 화면: `루틴이 다른 곳에서 변경되었습니다. 새로고침 후 다시 시도해주세요.`
- 팔 슬롯 없음: `교환할 팔 루틴을 찾을 수 없습니다.`
- 최대 블록 수 초과: 대상 목록에서 제외하고 서버에서도 거부
- RPC 미배포 또는 DB 오류: 데이터 변경 없이 오류 표시

## Testing Strategy

### Pure Logic

- 일차에서 팔 블록만 추출한다.
- 팔 블록을 교환하면서 비팔 블록과 순서를 보존한다.
- 결과가 일차당 3개 블록을 넘으면 거부한다.
- 같은 일차, 팔이 없는 일차, 범위 밖 일차를 거부한다.
- 팔 슬롯이 반복되는 일차만 대상으로 반환한다.

### Server and Schema

- RPC가 두 일차의 `arm` 행 `day_index`와 `custom_week`를 함께 교환한다.
- 운동 행 UUID와 모든 운동 속성이 보존된다.
- 예상 `custom_week`가 오래됐으면 아무 데이터도 변경하지 않는다.
- 오류가 발생하면 양쪽 변경이 모두 롤백된다.
- 다른 사용자의 행은 변경할 수 없다.

### End to End

```text
1일차: 등 + 이두 / 팔 운동 A
2일차: 어깨 + 삼두 / 팔 운동 B
```

교환 후 다음을 검증한다.

- 운동 등록 화면의 표기는 두 일차 모두 `팔`
- 1일차에는 팔 운동 B, 2일차에는 팔 운동 A가 표시됨
- 운동 행 UUID는 그대로이고 `day_index`만 교환됨
- `custom_week`는 1일차 삼두, 2일차 이두로 교환됨
- 운동 추가 목록은 이동한 내부 블록에 맞는 운동만 표시함
- 화면 어느 슬롯이든 미저장 변경이 있으면 교환되지 않음
- 워밍업·마무리와 과거 완료 기록이 변경되지 않음

## Non-Goals

- 팔 이외 부위 슬롯 교환
- 서로 다른 부위 간 교환
- 운동 한 행만 다른 일차로 이동
- 워밍업·마무리 교환
- 오늘만 변경 또는 과거 기록 교환
- 기존 커스텀 루틴 데이터 일괄 변환

## Acceptance Criteria

1. 운동 등록 화면에서 팔 관련 표기가 `팔`로 일관된다.
2. 팔 슬롯이 두 개 이상이면 대상 일차를 골라 교환할 수 있다.
3. 운동 데이터와 내부 팔 블록이 한 DB 트랜잭션으로 함께 교환된다.
4. 기존 운동 행 ID와 모든 속성이 보존된다.
5. 선택하지 않은 데이터, 컨디셔닝, 오늘만 데이터, 과거 기록은 변경되지 않는다.
6. 미저장 변경, 오래된 화면, 잘못된 대상, DB 오류에서 부분 교환이 발생하지 않는다.
